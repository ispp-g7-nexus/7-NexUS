# Plan de gestión ágil, seguimiento y calidad del proyecto

## 1. Objetivo del documento

Este documento define de forma clara y sencilla cómo vamos a trabajar durante el desarrollo del proyecto. Sirve para que todo el equipo tenga las mismas reglas, sepamos cómo medir el progreso y podamos demostrar al profesor que estamos gestionando el proyecto de forma organizada.

---

## 2. Rol del Scrum Master

El Scrum Master se encargará de:

* Asegurar que el equipo sigue la metodología acordada.
* Detectar problemas que estén frenando el trabajo.
* Ayudar a mejorar la organización del equipo.
* Hacer seguimiento del progreso de cada sprint.
* Evitar que se añadan tareas fuera de lo planificado.

No dirige el desarrollo ni reparte tareas técnicas. Su función es facilitar el trabajo y mantener al equipo alineado.

---

## 3. Onboarding inicial (puesta en marcha)

Al inicio del proyecto se hará una breve alineación para que todos partan del mismo punto:

* Explicar cómo vamos a trabajar por sprints.
* Revisar el stack tecnológico elegido.
* Explicar cómo usar repositorios, ramas y CI/CD.
* Aclarar roles y responsabilidades.

El objetivo es evitar confusión y empezar con una base común.

---

## 4. Organización del trabajo

* El proyecto se divide en sprints de 2 semanas.
* Cada equipo trabaja en módulos completos.
* Se prioriza usando MoSCoW (Must, Should, Could).
* Se intenta evitar dependencias entre equipos.
* Si hay bloqueos, se comunican lo antes posible.

---

## 5. Reuniones principales

### Sprint Planning (inicio del sprint)

* Se definen los objetivos.
* Se asignan módulos a cada equipo.
* Se estiman tareas.

### Seguimiento semanal

* Ver cómo va el trabajo.
* Detectar problemas.
* Ajustar si algo se está desviando.

### Sprint Review (presentación)

* Se enseña lo que se ha desarrollado.
* Se comparan resultados con objetivos.
* Se explican avances reales del producto.

### Sprint Retrospective (mejora)

* Qué ha salido bien.
* Qué ha salido mal.
* Qué podemos mejorar en el siguiente sprint.

---

## 6. Métricas que vamos a usar

Para saber si vamos bien o mal, mediremos cosas simples y claras:

### Progreso

* Historias planeadas vs historias terminadas.
* Porcentaje de tareas importantes (Must) completadas.
* Tareas que se pasan al siguiente sprint.

### Calidad

* Bugs detectados tras integrar cambios.
* Builds que fallan en CI/CD.
* Pull requests que necesitan muchos cambios.

### Producto

* Uso por parte de usuarios piloto (si aplica).
* Feedback recibido.

---

## 7. Cómo aseguramos la calidad

Una tarea solo se considera terminada cuando:

* El código funciona correctamente.
* Ha pasado los tests necesarios.
* Está revisado por otro compañero.
* Está subido al repositorio.
* La documentación básica está actualizada.

---

## 8. Seguimiento del proyecto

El Scrum Master revisará de forma continua:

* Si algún equipo está sobrecargado.
* Si hay retrasos acumulados.
* Si hay dependencias que bloquean el trabajo.
* Si se están añadiendo tareas fuera del sprint.

Si detecta problemas, se hablará con el equipo para buscar soluciones.

---

## 9. Estructura de las exposiciones de cada sprint

Para mantener orden y coherencia, cada presentación debería incluir:

1. Qué se planeó hacer
2. Qué se ha terminado realmente (con demo)
3. Problemas encontrados
4. Qué se ha aprendido
5. Qué se va a mejorar en el siguiente sprint

---

## 10. Mejora continua

Después de cada sprint se revisará:

* Qué ha funcionado bien.
* Qué no ha funcionado.
* Qué cambios podemos hacer para trabajar mejor.

La idea es mejorar la forma de trabajar poco a poco durante el proyecto.
